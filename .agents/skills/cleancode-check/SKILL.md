# CleanCode 检查技能

检查指定代码是否符合 CleanCode 编码规范，输出结构化检查报告。
   - 支持代码片段
   - git的diff文件或的代码片段
   - 编码文件

## 前置准备

规则查找工具位于 `scripts/find_code_rules.py`，规则文件位于 `scripts/rules/*.json`（每种语言一个 JSON 文件）。

脚本用法：
```
python3 scripts/find_code_rules.py --lang <语言>          # 获取某语言所有规则列表
python3 scripts/find_code_rules.py --rule-id <ID>         # 获取单条规则的完整 JSON 详情
python3 scripts/find_code_rules.py --code <规则编码>      # 按规则编码过滤
python3 scripts/find_code_rules.py --level <级别>         # 按严重级别过滤（致命/严重/一般/提示）
```

支持的编程语言：`Python`, `Java`, `Go`, `C`, `C++`, `JavaScript`, `TypeScript`, `Rust`, `Lua`, `Shell`，在此之外的语言

## 工作流程

### Step 1: 检查代码可疑点

分析用户提供的代码（文件或代码片段），识别所有可疑点。可疑点包括：

**安全类**
- 硬编码密钥/密码/Token（AccessKey、API Key、Secret、Password 等）
- SQL 拼接（字符串拼接构造 SQL 语句）
- 命令注入（`os.system`、`os.popen`、`subprocess(shell=True)` 等）
- 使用 `eval`/`exec` 执行不可信代码
- 正则表达式 ReDoS 风险（嵌套量词如 `(\d+)+`）
- XXE/XML 注入（未禁用外部实体的 XML 解析）
- 路径遍历（未校验的外部文件路径）
- 不安全的随机数（安全场景使用 `random` 而非 `secrets`/`os.urandom`）
- 不安全的文件权限（未指定权限创建文件）
- 不安全的反序列化/模板注入

**逻辑类**
- 不可达代码（`return`/`break`/`continue`/`raise` 之后的代码）
- 死循环（无退出条件的 `while True`）
- 返回值不一致（不同分支返回类型/数量不同）
- 异常被吞掉（空 `except` 或 `except: pass`）
- 资源未释放（文件/连接未关闭）
- 异常捕获顺序错误（父类异常在子类异常之前）

**设计类**
- 函数/方法过长或过于复杂
- 魔法数字/字符串（未定义为常量）
- 类职责过多（God Class）
- 过深的嵌套（if/for/try 嵌套超过 3 层）
- 参数过多（函数参数超过 5 个）
- 重复代码（相似逻辑出现多次）
- 子类未正确调用父类方法

**格式类**
- 命名不规范（变量/函数/常量命名不符合语言惯例）
- 注释缺失或 TODO/FIXME 未清理
- 文档字符串缺失（公共函数/类无 docstring）
- 行过长（超过 120 字符）
- 缩进不一致

对每个可疑点，记录：
- 文件路径（如果有）
- 行号（如果能定位）
- 可疑代码片段
- 可疑点类型（安全/逻辑/设计/格式）

### Step 2: 获取对应语言的规则

根据代码语言，获取该语言的所有 CleanCode 规则：

```bash
python3 scripts/find_code_rules.py --lang <语言>
# 例如：
python3 scripts/find_code_rules.py --lang Python
```

输出格式为字符串数组，每条格式为：`rule_id-语言-级别-规则编码-规则标题`

记录所有规则 ID 列表，用于后续逐条匹配。

### Step 3: 匹配可疑点与规则

将 Step 1 识别的可疑点与 Step 2 获取的规则进行匹配。匹配策略：

1. **直接匹配**：可疑点类型与规则标题/描述中的关键词直接对应
   - 例如：可疑点"硬编码密码" → 匹配规则标题含"禁止硬编码密码"的规则
   - 例如：可疑点"SQL 拼接" → 匹配规则标题含"拼接SQL"的规则

2. **语义匹配**：根据规则描述判断是否覆盖该可疑点
   - 读取规则详情后，判断规则描述是否涵盖可疑点的场景

3. **分类映射**：按可疑点类别映射到规则类别
   - 安全类可疑点 → 匹配 `G.EDV.*`（安全开发）、`G.DSP.*`（数据安全）、`G.FIO.*`（文件IO安全）等规则
   - 逻辑类可疑点 → 匹配 `G.CTL.*`（控制流）、`G.ERR.*`（异常处理）等规则
   - 设计类可疑点 → 匹配 `G.CLS.*`（类设计）、`G.EXP.*`（表达式）等规则
   - 格式类可疑点 → 匹配 `G.FMT.*`（格式）、`G.CMT.*`（注释）等规则

对每个匹配到的规则 ID，记录：
- 可疑点描述
- 匹配的规则 ID
- 匹配规则编码
- 匹配依据（为什么认为该规则适用）

### Step 4: 获取规则详情并分析匹配

对 Step 3 中匹配到的每个规则 ID，获取完整规则详情：

```bash
python3 scripts/find_code_rules.py --rule-id <rule_id>
```

对每条规则进行分析：

1. **确认匹配度**：
   - 规则描述是否完全覆盖可疑点场景？→ **完全匹配**
   - 规则描述部分覆盖可疑点场景？→ **部分匹配**
   - 规则描述与可疑点场景相关但不直接对应？→ **弱匹配**

2. **评估严重性**：
   - 规则级别（致命/严重/一般/提示）
   - 结合可疑点的实际风险等级，判断是否需要升级或降级

3. **检查修复建议**：
   - 规则是否提供了 `fix_suggestion`？
   - 修复建议是否具体可操作？
   - 是否需要补充额外的修复建议？

4. **排除误报**：
   - 代码中是否真的存在该问题？（有些可疑点可能是误判）
   - 规则是否适用于当前代码上下文？（例如某些规则仅适用于特定场景）

### Step 5: 输出分析报告

**铁律：只输出有问题的项，没问题的不输出。零噪音。**

#### 情况 A：发现 CleanCode 问题

```markdown
# CleanCode 检查报告

## 检查概要
- **检查语言**: Python
- **检查文件**: file1.py, file2.py
- **确认问题数**: K

## 问题统计
| 级别 | 数量 |
|------|------|
| 严重 | 2 |
| 一般 | 1 |

## 详细问题

### 问题 1: 硬编码密码
- **文件**: xxx.py
- **行号**: L42
- **规则ID**: 870 | **规则编码**: G.VAR.S.097
- **级别**: 一般
- **问题描述**: 硬编码的密码可能会被滥用以获取未经授权的访问并破坏安全边界。
- **可疑代码**:
  ```python
  password = "admin123"
  ```
- **匹配依据**: 变量名含 password 且赋值为字符串字面量
- **修复建议**: 使用环境变量或密钥管理服务存储密码
- **匹配度**: 完全匹配

### 问题 2: ...

## 总结与建议
[整体代码质量评估和改进建议]
```

#### 情况 B：未发现 CleanCode 问题

```markdown
# CleanCode 检查报告

## 检查概要
- **检查语言**: Python
- **检查文件**: file1.py
- **确认问题数**: 0

## 结论
未发现 CleanCode 问题。
```

#### 情况 C：有可疑点但全部排除（无确认问题）

```markdown
# CleanCode 检查报告

## 检查概要
- **检查语言**: Python
- **检查文件**: file1.py
- **可疑点总数**: N
- **确认问题数**: 0

## 排除的可疑点
| 可疑点 | 排除原因 |
|--------|----------|
| [可疑点描述] | [为什么排除] |

## 结论
发现 N 个可疑点，经分析均不构成实际问题。
```

#### 严格禁止输出的内容

- 不要输出"误报说明"章节（除非有实际排除的可疑点）
- 不要输出"总结与建议"章节（除非有确认问题）
- 不要输出空的问题列表或占位符（如 `### 问题 2: ...`）
- 不要输出"通过"的规则或代码片段
- 不要输出"检查概要"中的"匹配规则数"等无意义统计
- 不要输出空的问题统计表（全部为 0 时省略该表）
- 不要输出"规则字段说明"、"规则类别说明"等参考信息（这些是技能内部知识，不是报告内容）
- 不要输出"可疑点总数"（除非有排除的可疑点需要展示）
- 不要输出任何"通过检查"的正面评价（没问题是常态，不需要强调）

#### 输出精简原则

1. **有则报，无则不报** — 每个章节必须有实际内容才输出
2. **问题按严重级别排序** — 致命 > 严重 > 一般 > 提示
3. **同一文件的相邻问题合并** — 不要为同一行代码输出多个重复问题
4. **可疑代码只展示问题行** — 不要展示整个函数或文件
5. **修复建议优先用规则自带的** — 规则没有时才补充

## 规则字段说明

每条规则包含以下字段：
| 字段 | 说明 |
|------|------|
| `rule_id` | 规则唯一ID |
| `code` | 规则编码（如 G.CLS.01） |
| `title` | 规则标题 |
| `language` | 适用语言 |
| `level` | 严重级别（致命/严重/一般/提示） |
| `description` | 规则详细描述 |
| `fix_suggestion` | 修复建议 |

## 规则类别说明

| 类别前缀 | 含义 | 示例 |
|----------|------|------|
| `G.VAR.*` | 变量相关 | 硬编码、命名规范 |
| `G.CLS.*` | 类设计 | 继承、方法签名、魔法函数 |
| `G.CMT.*` | 注释规范 | 文档字符串、TODO/FIXME |
| `G.CNP.*` | 并发相关 | 子进程、线程安全 |
| `G.CTL.*` | 控制流 | 循环、条件、返回值 |
| `G.DSP.*` | 数据安全 | 加密、随机数、传输安全 |
| `G.EDV.*` | 安全开发 | SQL注入、命令注入、XSS |
| `G.ERR.*` | 异常处理 | 异常捕获、抛出、传递 |
| `G.EXP.*` | 表达式 | lambda、推导式 |
| `G.FIO.*` | 文件IO | 文件权限、路径、临时文件 |
| `G.FMT.*` | 代码格式 | 缩进、行宽、空行 |

## 示例

### 示例1：检查 Python 代码

用户："帮我检查这段 Python 代码的 CleanCode 问题"

```python
def process_data(user_input):
    password = "admin123"
    query = "SELECT * FROM users WHERE name = '" + user_input + "'"
    os.system("echo " + user_input)
    result = eval(user_input)
    return result
```

执行流程：
```bash
# Step 2: 获取 Python 规则
python3 scripts/find_code_rules.py --lang Python

# Step 3: 分析到意思问题rule-id:870、903、899、898

# Step 4: 获取匹配规则详情
python3 scripts/find_code_rules.py --rule-id 870  # 禁止硬编码密码
python3 scripts/find_code_rules.py --rule-id 903  # 禁止拼接SQL
python3 scripts/find_code_rules.py --rule-id 899  # 禁止OS命令解析器
python3 scripts/find_code_rules.py --rule-id 898  # 禁止eval执行不可信代码
```

输出分析报告（按 Step 5 格式）。

### 示例2：查看某条规则详情

用户："G.CLS.01 规则是什么？"

```bash
python3 scripts/find_code_rules.py --code G.CLS.01
# 或
python3 scripts/find_code_rules.py --rule-id 871
```

### 示例3：按级别筛选规则

用户："Python 有哪些严重级别的规则？"

```bash
python3 scripts/find_code_rules.py --lang Python --level 严重
```
