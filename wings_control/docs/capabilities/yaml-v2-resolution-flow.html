Wings YAML v2 裁决流程

用户下发 → 候选 → 偏序 → 歧义 / 最终参数 —— 用 demo 资产举例说明 profile 泛化/特化（偏序裁决）的完整过程

流程总览

一次 v2 资产查找（locate_v2）经历四个阶段：用户下发构造查找上下文（ctx）→ 候选逐 key 匹配筛选 → 偏序按匹配集合包含选最特化者 → 歧义 / 最终参数裁决并渲染启动参数。

输入 匹配 裁决 输出

①用户下发：构造查找上下文（ctx）

调用方（MaaS / CLI）下发模型名、硬件、引擎版本等，Wings Control 组装成查找上下文 ctx。必填四要素（engine/version/hardware/model）始终存在；context_length 是可选 key，由用户下发的 max_model_len（= input + output 总上下文窗口）派生；cpu_arch 是可选 key，由运行时 platform.machine() 探测派生。

CLI 下发

ENGINE_VERSION=v0.99.0 python -m wings_ctl \
  --model-name TestModel \
  --hardware-info hardware_info.json \
  --engine vllm-ascend \
  --dry-run \
  --input-length 200000 \
  --output-length 0

dry-run 只做启动前推演，不写文件、不启动 engine。

组装后的 ctx

ctx = {
  "engine": "vllm-ascend",
  "version": "v0.99.0",
  "hardware": "Ascend910C_64G",
  "model": "TestModel",
  "context_length": 200000,
}

硬件别名会先归一化（如 Ascend910_64G → Ascend910C_64G）再匹配。

②候选：逐 key 匹配（evaluate_profile）

扫描器递归遍历 v2 资产树（目录仅作物理组织，不参与匹配），对每个 yaml 的 profile 块逐 key 用 ctx 求值。所有 key 命中才进入候选集合；任一未命中（含 ctx 缺值）→ 拒绝。

三个候选资产（demo：TestModel）

# TestModel-fallback.yaml（不写 context_length）
profile:
  engine: vllm-ascend
  version: "v0.99.0"
  hardware: {Ascend910C_64G}
  model: TestModel
  # 不写 context_length → 最泛化
# TestModel-generic.yaml（context_length >= 0）
profile:
  engine: vllm-ascend
  version: "v0.99.0"
  hardware: {Ascend910C_64G}
  model: TestModel
  context_length: { ">=": 0 }
# TestModel-longctx.yaml（context_length >= 131072）
profile:
  engine: vllm-ascend
  version: "v0.99.0"
  hardware: {Ascend910C_64G}
  model: TestModel
  context_length: { ">=": 131072 }

ctx = { context_length: 200000 } 时的匹配结果

资产engineversionhardwaremodelcontext_length结果
TestModel-fallback.yaml ✅✅✅✅ 未声明，不校验 命中
TestModel-generic.yaml ✅✅✅✅ 200000 ≥ 0 ✅ 命中
TestModel-longctx.yaml ✅✅✅✅ 200000 ≥ 131072 ✅ 命中
关键点：不写 context_length 的资产在候选阶段不校验该 key（for 循环不遍历它），只要必填四要素命中就进入候选。写了 context_length 的资产若 ctx 缺该值则直接拒绝。

③偏序：选最特化者（is_more_specific）

候选集合内，偏序引擎按匹配集合包含判定特化程度：A 比 B 更特化 ⟺ A 的匹配集合 ⊆ B 的匹配集合（且至少一个参与偏序的 key 严格包含）。仅 partial_order=True 的 key（hardware 集合包含、cpu_arch 集合包含、context_length 区间包含）参与偏序。

context_length 区间包含

三个候选的匹配集合关系：不写（全集）⊇ >=0 ⊇ >=131072，故 >=131072 最特化。

偏序链：不写（最泛化） < >=0 < >=131072（最特化）。ctx=200000 落在 >=131072 区间内，故 TestModel-longctx.yaml 最特化。

hardware 集合包含（另一维度）

hardware 用集合包含判定：{Ascend910C_64G} ⊆ {Ascend910C_64G, Ascend910B_64G}，故单硬件资产更特化。

④歧义 / 最终参数（resolve 裁决）

resolve 从候选集合中淘汰被更特化者覆盖的候选，选出唯一最特化者。若多个候选等价（重复资产）或互不偏序，则报歧义 → locate_v2 告警 + 确定性选第一个（按资产路径排序，可复现）。

正常路径：唯一最特化 → 选中

ctx = { context_length: 200000 }，三个候选都命中。偏序淘汰：fallback（最泛化）和 generic（>=0）都被 longctx（>=131072）覆盖 → 选中 TestModel-longctx.yaml。

候选匹配集合是否被更特化者覆盖结果
TestModel-fallback.yaml全集被 generic / longctx 覆盖淘汰
TestModel-generic.yaml>=0被 longctx 覆盖淘汰
TestModel-longctx.yaml>=131072无选中

最终参数渲染

选中资产后，其 scenarios.standalone.strategies.single_node.engine_config 与 env 参与 trace-first 合并，渲染出 engine 启动命令与环境变量。dry-run 打印预览：

# Environment Variables
export OMP_NUM_THREADS=10
export HCCL_BUFFSIZE=1024
export RAG_ACC_ENABLED=false

vllm serve /root/.cache/modelscope/hub/models/TestModel \
  --host 0.0.0.0 --port 8900 \
  --max-model-len 200000 \
  --max-num-batched-tokens 8192 \
  --served-model-name TestModel \
  --gpu-memory-utilization 0.9 \
  --max-num-seqs 64 \
  --tensor-parallel-size 4 \
  --data-parallel-size 1 \
  --quantization ascend \
  --block-size 128
对比：若 ctx = { context_length: 4096 }，则 longctx（>=131072）不命中，generic（>=0）胜出，渲染出通用参数（--max-num-batched-tokens 1024、--gpu-memory-utilization 0.8、--max-num-seqs 32）。这就是"不同上下文长度 → 不同启动参数"的泛化/特化。

歧义路径：等价 / 互不偏序 → 告警 + 选第一个

等价重复资产

# AmbiguityDemo.yaml 与 AmbiguityDemo-dup.yaml
# profile 完全相同 → 匹配集合相同 → 等价
profile:
  model: AmbiguityDemo
  context_length: { ">=": 0 }

告警 + 选第一个（按路径排序，-dup 在前）。

互不偏序

# IncomparableDemo-a.yaml
context_length: { ">=": 100 }

# IncomparableDemo-b.yaml
context_length: { "<=": 200 }

>=100 与 <=200 互不严格包含（谁都不比对方更特化）→ 互不偏序 → 告警 + 选第一个。

# 歧义告警示例（节选，实际末尾含候选 profile 列表）
WARNING v2 asset ambiguity; picking the first matched asset:
ambiguous profile resolution: 2 candidates are equally specific
(duplicate assets or incomparable profiles)
歧义需资产作者离线人工比对解决（声明更特化配置或合并；离线校验脚本只做单资产合法性检查，不检测跨资产等价/互不偏序）；运行时先跑起来，避免因数据歧义阻断启动。
